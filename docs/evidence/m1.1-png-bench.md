# M1.1 PNG codec: peak RSS and time

Recorded by `node tools/png-bench.ts` on 2026-10-02. Threat-model row R4.2-08;
02 §5 budget: one decode/compare at a time within 512 MiB.

- Machine: AMD Ryzen 5 3600 6-Core Processor, 12 logical CPUs, 16 GiB RAM, win32 10.0.22621
- Node v22.19.0; commit `b617f36`, `packages/core/src` tree `9248ca3`
- Each row: 3 runs, each in a fresh Node process. Times are medians in ms. Peak RSS is the
  largest `process.resourceUsage().maxRSS` of the runs, in MiB, and includes Node itself (see
  `baseline`) and reading the input file.
- Total is the measured work from the first codec call to the end, including a rejection.
- Encoded bytes is the canonical PNG's size (canonicalize rows only).

| Scenario | Input | Input bytes | Outcome | Decode | Hash | Encode | Total | Encoded bytes | Peak RSS |
|---|---|---|---|---|---|---|---|---|---|
| baseline | Node + core modules loaded, input read, no codec call | 90,342 | no codec call | – | – | – | 0 | – | 75 |
| real-decode | Largest committed real screenshot, 1440×1013 RGB, 23 IDATs | 90,342 | decoded | 36 | 17 | – | 54 | – | 92 |
| real-canonical | Same, decode + hash + canonical encode | 90,342 | decoded | 37 | 19 | 171 | 227 | 89,801 | 96 |
| tall-decode | Synthetic 1440×6000 RGB (PropertyScope's tallest) | 163,615 | decoded | 182 | 93 | – | 275 | – | 136 |
| tall-canonical | Same, decode + hash + canonical encode | 163,615 | decoded | 164 | 93 | 726 | 984 | 100,236 | 136 |
| max-decode | Synthetic 4000×4000 RGBA (16 MP limit) | 314,670 | decoded | 425 | 160 | – | 584 | – | 173 |
| max-canonical | Same, decode + hash + canonical encode | 314,670 | decoded | 413 | 185 | 2153 | 2717 | 297,122 | 202 |
| max-worker | Same, decoded in a PngWorker (process RSS includes the worker) | 314,670 | decoded | 792 | – | – | 801 | – | 194 |
| many-idat | Hostile shape: 2,551,241 one-byte IDAT chunks (31.6 MiB), valid 1000×850 RGB | 33,166,178 | decoded | 1584 | 11 | – | 1595 | – | 125 |
| bomb | Hostile: 4000×4000 RGBA inflate bomb (64 MB + 1 MiB of zeros) | 63,303 | rejected `inflate-overflow` | – | – | – | 71 | – | 169 |
| too-large | Hostile: 32 MiB + 1 byte | 33,554,433 | rejected `too-large` | – | – | – | 0 | – | 112 |

`decodePng` inflates once, straight into the output buffer the checked header sizes. The bomb
allocates that 64,000,000-byte buffer and is refused one 64 KiB piece past the expected size; it
never writes past it (`packages/core/test/png-decode.test.ts` checks that a hostile file
allocates at most that one buffer). Only this Windows machine was measured; CI runs the same code
on Linux but doesn't record RSS.
